# review-pr — one review pass over a set of pull requests

Usage:

```text
/review-pr [<pr> ...] [--mode ask|auto]
```

- `<pr>` is a bare number (`123`) for the current repo, or a full PR
  URL for any repo. Several may be given. With none, use the PR for the
  branch checked out in the current directory (`gh pr view`).
- `--mode ask` (default): ask the person running the skill at the two
  decision points below (review again when nothing changed; post the
  draft). Wait for the answer.
- `--mode auto`: never ask. Nothing new means no review; a draft is
  posted as soon as it is written. This is the mode for a loop.

Every run is one pass and ends with a run table and one report line
per PR. The record of a review is the PR itself: the review it posts,
which opens with the same run table and carries the marker the next
pass reads, and the inline comments, each marked with its finding id.
Beside that record the skill keeps one index per PR, a git ref on
origin, `refs/review-pr/<number>`, holding the claim, the findings and
how each was answered. `review-state.mjs` beside this file reads and
writes it; call it as `node <skill-dir>/review-state.mjs`. The ref is
only an index: once the PR is claimed, step 3 rebuilds it from the PR
whenever the PR has a review of ours. The skill keeps no files of its
own.

This skill reads code and posts reviews. It never edits, commits, or
pushes on the PR's branch, never merges, closes, or approves a PR, and
never resolves a thread. Answering review comments is `/check-pr`'s job.

# Agent work identity

At the start of each pass, record one identity for the work the pass performs.
Use it unchanged in every review, comment, response, marker, and final report
from that pass.

| Skill | `<skill-name>@<plugin-version>` from the host's plugin manifest; `<skill-name>@dev` when there is no manifest (a development tree); `<skill-name>@unknown` only when a manifest exists but has no version |

## Remote for the state script

`review-state.mjs` writes to a git remote. Decide once per PR whether it belongs to the repository
the checkout's `origin` points at: normalise `origin`'s URL to `owner/repo` and compare it,
case-insensitively, with the PR's `owner/repo`.

```sh
git remote get-url origin | sed -E 's#^(git@|ssh://([^@/]+@)?|https?://([^@/]+@)?)github\.com[:/]##; s#(\.git)?/?$##'
```

It handles `git@github.com:o/r.git`, `https://github.com/o/r(.git)`, `ssh://git@github.com/o/r` and
URLs carrying `user[:token]@`. When they match, omit `--remote`. For a PR in any other repository,
add `--remote https://github.com/<owner>/<repo>.git` to every call; it takes a URL as well as a
remote name, and works from a directory that is not a git repository. A GitHub Enterprise or other
non-`github.com` host does not normalise: always pass an explicit `--remote <url>` there.

Pass a PR's commit as the full 40-character sha everywhere a sha is recorded (`fixed in <sha>`,
`--fixed-in`, `--head`, `--base`).

## 1. Resolve the PRs

For each argument, fetch one snapshot:

```sh
gh pr view <pr> -R <owner>/<repo> --json number,url,title,body,state,isDraft,author,headRefName,headRefOid,baseRefName,headRepositoryOwner,reviews,comments
```

Every `gh` call that takes a PR passes the PR's repository (`-R <owner>/<repo>`, or the full PR
URL in place of the number), because the working directory may be a clone of another repository and
a bare number resolves against it. `gh api` paths already carry `<owner>/<repo>`.

Record who "we" are once per run: `gh api user --jq .login`. A review
by that login is ours.

Record the shared identity once before the first PR. `session` is also the
`--owner` of every `claim`, `record` and `release` call. The detailed review record and the final
report use those values.

Every `review-state.mjs` call writes to a git remote. The shared instruction above says how to
compare `origin` with the PR's repository and when to add `--remote <url>` to every call; the calls
below are written without it.

A PR whose `state` is `MERGED` or `CLOSED` gets a report line with `REVIEW=closed` and one bit of
housekeeping: `node <skill-dir>/review-state.mjs archive <number>` moves its ref to
`refs/review-pr/archive/<number>`. With no live ref it exits 0 and prints
`{"archived":false,"reason":"no live state"}`; any other failure is reported. It gets no other
work. When the person named that PR explicitly (it was not found by the branch checked out), say in
the closing note that it is merged or closed and was not reviewed. A draft PR is reviewed like any
other; the author asked by naming it.

## 2. Find the last review and decide what to do

The head commit under review is `headRefOid`; call it `head`. Its `base` is
`git merge-base <head> origin/<baseRefName>`, after `git fetch origin <headRefName> <baseRefName>`
(for a fork, `git fetch origin pull/<number>/head`). Use the full 40-character shas everywhere.

Every review this skill posts ends with a marker line:

```text
<!-- review-pr: head=<full sha> base=<full sha> -->
```

`head` is the commit the review covered and `base` is the merge-base
of that commit with the base branch at the time. A marker may carry
further `key=value` pairs after these two (step 6 writes the run
record there); this step reads only `head` and `base`. Search our own
reviews (`reviews[]` where `author.login` is us) that carry the marker, and
skip any of ours that do not (check-pr posts empty reply-reviews), then
take the one with the latest `submittedAt`. Call its values `last`
and `last_base`. No marker means this PR has never been reviewed by
this skill.

Then:

- **No marker**: claim the PR (step 3), then a full review (step 4).
- **`last == head`**: nothing has changed since the last review.
  With `--mode auto`, report `REVIEW=unchanged` and do nothing else
  for this PR. With `--mode ask`, say when the last review was posted
  and ask whether to review again anyway. Yes means claim, then a full
  review; no means `REVIEW=skipped`.
- **`last != head`**: claim the PR (step 3), then a delta review
  (step 5).

Base movement alone does not change the answer. The changeset is the
commits on the head branch, and those are the same until `head` moves.

## 3. Claim the PR and bring its index in line

Several sessions, on this machine or others, may run this skill against
one repository at the same time, and the marker only exists once a
review is posted. Between deciding to review and posting, a claim keeps
two sessions from doing the same work and posting twice. The claim lives
in the PR's ref on origin and is written with compare-and-swap, so a
race resolves to one owner:

```sh
node <skill-dir>/review-state.mjs claim <number> --owner "<session>"
```

- Exit 0: the claim is ours. A claim 60 minutes old or more belonged to
  a dead session and was taken over; the output says so
  (`tookOver`), and the report should too.
- Exit 4: another session holds the PR. Report `REVIEW=claimed` with the
  owner from the output and do nothing else for this PR.
- Exit 3: lost the race twice; treat it as exit 4.
- Exit 1: the remote could not be reached or refused the write. Report
  the error for that PR and move on; do not review without a claim.

The claim is held for the whole pass, through the post. `record` (step
6) keeps it. Every ending releases it once the pass for this PR is over:
after posting, on `REVIEW=skipped`, on an exit 4 from `record`, and on
any error after the claim:

```sh
node <skill-dir>/review-state.mjs release <number> --owner "<session>"
```

`release` drops only a claim this session owns, so a takeover is not
undone.

With the claim held, read the index:

```sh
node <skill-dir>/review-state.mjs read <number>
```

Exit 1 (an unreachable remote) is an error for this PR: release the claim,
report it and move on. A corrupt state (`corrupt state` in the error, which
`claim` can hit too) is repaired, not an error: run the rebuild below, and
when the PR has no review of ours with a marker run
`node <skill-dir>/review-state.mjs rebuild <number> --from empty.json` with `empty.json` holding
`{"head":null,"base":null,"round":0,"findings":[]}`. Then claim again if the claim had failed.

If the PR has a review of ours with a marker, rebuild the index from the
PR every time, whatever the index says. The PR is the record; the index
may have missed an answer, or a person may have replied `declined:` by
hand. With no marker there is nothing to rebuild; the ref first exists once `claim` writes it.

```sh
gh api --paginate repos/<owner>/<repo>/pulls/<number>/reviews > reviews.json
gh api --paginate repos/<owner>/<repo>/pulls/<number>/comments > comments.json
node <skill-dir>/review-state.mjs from-pr <number> --reviews reviews.json --comments comments.json \
  --me <actor> --author <PR author login> --out rebuild.json
node <skill-dir>/review-state.mjs rebuild <number> --from rebuild.json
node <skill-dir>/review-state.mjs read <number>
```

`from-pr` reads our review markers, the finding markers on inline comments and in review bodies, and
the `declined:` / `fixed in <sha>` replies in their threads, and writes the `rebuild` input. Use the
findings from the final `read` from here on. Put the three files in a scratch directory, not the
repo.

## 4. Full review

If `read` listed findings, they came from an earlier review of this PR
(the person asked for another pass, or step 5 fell back to a full
review). Give the judging agent the open findings and the declined ones
with their reasons, and tell it not to raise a declined finding again
unless the code changed so that it is newly true.

Bring the commit within reach. Fetch it first: `git fetch origin <headRefName>` for a branch in this
repo, or `git fetch origin pull/<number>/head` for a fork. Reading through `git show <sha>:<path>`
and `git diff` needs no checkout. When you want files on disk, add a detached worktree at `head`:

```sh
git worktree add --detach <repo-root>/.worktrees/review-<number> <head>
```

If the repo has its own worktree convention, use that location
instead. Remove the worktree when the pass is done. Never commit in it.

Read the change with `git diff <base>...<head>` and
`git log <base>..<head>`, the PR description and prior discussion.
Then review it the way `/code-review` does; its rubric follows.

Review like a senior engineer who has shipped the incident this code
could cause. Prefer a concrete example of the failure over an abstract
"this could be safer". If the fix is a one-liner, give it in the finding
rather than only naming the problem.

Read the changed files, not just the diff hunks. A renamed variable or a
shifted guard clause often only makes sense in context. When a change
alters a contract, follow the function to its callers.

Report, in order of severity. Each category below carries its own rules.
Report a defect once, under the category that states its harm. Report one
finding per concrete instance. Judge what the change adds or alters; code it
does not touch is out of scope unless the change makes it newly wrong.

### 1. Errors

Bugs, broken contracts, and behaviour the change description promises that
the code does not deliver. Failure handling is judged separately, right after.

#### Correctness

Correctness is whether the code does what the change says it does, and
whether it still does when the input is hostile or the timing is unlucky.
These are the defects that reach production and cost the most, so they come
first. A finding here names a concrete input, ordering or caller for which the
code is wrong.

Look for:

- Behaviour the description, commit message, comment or name promises that the
  code does not deliver.
- Logic and boundaries: off-by-one, empty and single-element input, null or
  missing values, an inverted condition, the wrong operator, integer, time-zone
  and encoding edges.
- Broken contracts: a changed signature, return shape or invariant with a
  caller that still assumes the old one. Follow the function to its callers.
- Concurrency and ordering: a check followed by an act across an await or a
  thread boundary, shared mutable state, a read before the write it needs,
  unawaited work, cleanup that depends on order.
- Resource leaks: processes, file handles, subscriptions, timers, transactions
  and connections opened and not released on every path.
- Input trust: a value from a user, file, network, environment variable or
  subprocess used as a path, key, index, size or command without validation at
  the point it enters.
- Injection: untrusted text placed into a shell command, SQL, path, regex, HTML
  or prompt without escaping or an argument array.
- Secrets: a token or credential reaching a log line, error message, artifact
  or command line.
- Authentication and authorization: a caller-controlled value (a header, a
  path, an id) trusted to grant access; one actor able to act with another's
  authority; a check placed after the action it guards.
- A dry-run or read-only mode that still writes, spawns, pushes or posts.

Not a finding:

- Pre-existing code the change leaves untouched, unless the change makes it
  newly reachable.
- A guard that the surrounding code already provides. Read the callers and
  callees before reporting.
- Defences against inputs the program cannot produce, such as validating a
  value the type system already constrains.
- Style, naming and anything a linter or type checker reports.

Writing the finding: cite file:line. State the failing input or sequence
("two calls interleaved at the await on line 40 both pass the check") or, for
a security finding, who controls the value and what it reaches. Give the fix
when it is a line or two.

#### Error paths

Error paths are the least exercised code in a change and the code that runs
when someone is already in trouble. A swallowed error turns a loud failure into
silent corruption; a missing cleanup turns one failure into a pile-up on the
next run. Judge each catch, error branch, failure result, non-zero exit and
fallback the change adds or alters.

Look for:

- Swallowed errors: an empty catch, a discarded failure result, a fallback
  that hides the cause, a promise rejection nobody observes.
- Partial writes: if step N of M fails, what is left behind (a half-written
  file, a held lock, a created directory, a posted message)? Can a later run
  detect it and recover?
- Cleanup: temp files, locks, processes, sessions and handles released on every
  exit path, including the failing one.
- Retries: bounded, backed off, limited to errors that can succeed on retry,
  and applied only to operations that are safe to repeat.
- Exit codes: a failure that exits zero, or an error that is logged and then
  treated as success by the caller.
- Messages: an error that names what failed, on which input, and what the
  reader can do next, without leaking a secret. One generic message for several
  distinct causes is a finding when the reader must act differently on each.
- Inconsistency: a new helper that returns null on failure where its siblings
  throw, so callers handle two conventions.

Not a finding:

- A deliberate, commented best-effort step whose failure the caller does not
  depend on (for example removing a cache file that may not exist).
- Handling at the right layer: an error passed up unchanged to a caller that
  handles it is correct. Do not ask every function to catch.
- Errors the language or framework already reports with a usable message.
- Formatting or naming of error text, and anything a linter catches.

Writing the finding: cite file:line. Trace the failure: name the failing call,
what the code does next, and the state or message that results. Name the
missing cleanup or the lost cause, and give the fix, such as a finally block, a
rethrow with context, or a cap on the retry loop.

### 2. Missing coverage

Behaviour the change alters without a test that would catch a regression in
it, including each new error branch. Say plainly which changed behaviour has
no test.

### 3. Duplication

Duplication is logic, strings or types the change writes that already exist,
or that now exist in two places. Two copies drift: a fix lands in one and the
other keeps the bug. The cheapest time to remove a copy is the diff that adds
it. The fix is to call the existing code, or to move the shared part to one
home both callers use.

Look for:

- A helper, type or constant the change declares that the repo already
  exports under another name. Search by behaviour, not only by name: grep for
  the distinctive call, regex or literal.
- A block copied from elsewhere with small edits, where the differences could
  be parameters.
- The same string literal, message, path or magic number written in several
  places, so changing one means finding the rest.
- A new implementation of something the change's own feature generalizes: the
  old bespoke version left standing beside its replacement.
- Parallel types or schemas that must be edited together to stay correct.

Not a finding:

- Similar shape with different meaning. Two loops over different data, or two
  functions that happen to look alike but change for different reasons, are
  not one concept. Merging them couples things that should move apart.
- Test fixtures, test setup and expected values. A test that spells out its
  data is easier to read than one that shares a builder with ten others.
- Two similar blocks when neither is a callable shared symbol. Name them if
  they are clearly the same concept, but do not demand an abstraction until a
  third copy appears or the shared meaning is clear. Re-implementing a helper
  the repo already exports is always a finding.
- Generated files, vendored code, and repetition a formatter or linter already
  reports.

A private helper that a second consumer should call, rather than copy, is a
modules finding, not a duplication finding.

Writing the finding: cite the new code and the existing code, each as
file:line. Name the canonical home: the existing symbol to call, or the
module where the shared version should live. Say what differs between the
copies, if anything, so the author can tell whether a parameter is enough.

### 4. Modules and structure

Modules and packages are how a codebase reuses work. Two failures cost the
most: code that hand-rolls what an existing package already provides, and
code with a clear second use that stays buried where it was written. The
opposite failure is just as real: a shared package created for one caller.
By default, co-locate first and promote when a second consumer appears, and
keep each module's public surface small. Where the project's instruction files
or standards place code differently, follow them.

Look for:

- Hand-rolled code for something the project already depends on or names in
  its library roster: argument parsing, schema validation, retry logic, path
  handling, date handling, a git or process wrapper. Read the project's
  instruction files (CLAUDE.md, AGENTS.md) and any library roster they name,
  and look at the shared-package directory they point to, before judging.
- A helper general enough that a second consumer is visible in the diff or in
  the repo, but still private to one file. Name the consumer and the module it
  should move to.
- A new shared module or package with one caller and no sign of another.
  Suggest keeping it beside that caller until a second one exists.
- Reaching into another module's internals: deep imports past its entry
  point, reading its private files, or depending on its non-public types.
- Test-only exports: a symbol exported from a module only so a test can reach
  it. Test through the public surface, or move the logic to a module whose
  public surface it belongs on.
- A module whose public surface grew by more than the change needs, or a
  dependency edge that points the wrong way (a low-level module importing a
  higher-level one).

Not a finding:

- Boundary rules a linter or import checker already enforces. Flag a boundary
  break only when no such tool covers it.
- A small helper used once. Duplicating five lines is cheaper than a package.
- A deliberate choice the project's instruction files or standards document,
  such as a preferred library for one job or a rule on where capabilities
  live.
- File placement that matches how the neighbouring files are organized.

Writing the finding: cite file:line. For a missed package, name the package
and the function to call. For a promotion, name the second consumer and the
destination module. For a boundary break, name the import and the public entry
point to use instead.

### 5. Cleanup

Dead code, naming drift, departures from the conventions of the surrounding
code, and comments that fail the comment rules below: a comment the change
made wrong, one that restates the code, one that pins a count or version
nothing keeps true, or a fact that belongs in a name, a type, or the
declaration's doc annotation.

### Reporting

Skip anything the repo's linters and formatters already catch. Before
flagging naming or formatting that CI does not cover, check it against the
house style:

- Functions read top to bottom: the happy path first, guard clauses after.
- Booleans are named as a question (`isReady`, `hasChanges`), never
  `flag` or `ok`.
- A comment explains why, never what.
- No commented-out code in a merged diff. Delete it; git remembers.

Cite the file and line for every finding, most severe first. Re-open the
file and confirm the line before writing the finding down; a wrong finding
costs more than a missed one. Say "no findings" for an empty category
rather than padding.

Comments are judged by the rules `/comment-review` applies as verdicts:

The rules a comment is judged by: where a fact belongs, what earns an inline
comment, how a kept comment reads, and when a comment is a duplicate of
something with a better home. `/comment-review` applies them as verdicts; `/code-review`
and `/review-pr` apply them to the comments in a diff.

### The expression ladder

A fact about code has exactly one right home. Work down this list and stop at the
first rung that can carry it:

1. **The identifier.** A function, variable, type, or constant whose name states
   the fact needs no comment stating it. `// retry three times` above
   `const n = 3` is `const MAX_RETRIES = 3`.
2. **The signature and the types.** Parameter names, a union instead of a string,
   a non-null return instead of a documented "never null", an options object
   instead of three positional booleans. A comment describing what a type already
   guarantees is a duplicate of the type.
3. **The declaration's doc annotation.** One block on the declaration, for the
   contract a *caller* needs and cannot read off the signature: what the function
   promises, what it throws, what it mutates, what invariant it assumes on entry.
   Facts a caller needs go here, not scattered inline where a caller never looks.
   Use the language's own annotation form rather than a loose block above the
   declaration — TSDoc `/** */` with `@param`, `@returns`, `@throws`; rustdoc
   `///` with `# Errors` and `# Panics`; the docstring in Python. The native form
   is what tooling, hovers, and generated docs read, so a fact written there
   reaches the caller where a bare `//` above the line does not. A per-parameter
   fact belongs in that parameter's tag, not in an inline comment beside the
   argument.
4. **An inline comment.** Everything left over — and only what is left over.

### What earns an inline comment

Only a fact a competent reader cannot deduce from the code in front of them:

- **The why**, where the obvious alternative was tried and does not work. Name the
  alternative and what broke.
- **An empirical fact about the outside world** — an API's undocumented behavior, a
  browser or runtime bug, a measured cost. Facts nothing in the file can imply.
- **A non-local constraint** — an ordering another file depends on, an invariant
  held elsewhere, a call this code must not make.
- **A deliberate deviation** from a convention the reader will otherwise read as a
  mistake.
- **A pointer to an external cause** — an issue, a spec section, a decision entity.

Everything else is noise. In particular these never earn one: restating the
statement below it; naming a block (`// loop over the items`); describing a
parameter the signature already names and types; change history; decorative
banners and section rules; a summary of a well-named function's body; a count or
other project measurement that nothing keeps true.

### How a kept comment reads

A comment that earns its place still has to be worth reading. A comment that
is kept or rewritten obeys four rules:

- **Short.** One or two sentences. A comment that needs a paragraph is usually a
  fact with a home further down the ladder, or one that belongs in documentation.
- **Plain and literal.** State the fact directly. No metaphor, no analogy, no
  jokes — a reader who does not share the reference has to decode the sentence
  before they can use it, and a metaphor that drifts from the code cannot be
  detected as wrong.
- **Descriptive, not evaluative.** "Runs before the index is built" is a fact.
  "Careful here!" and "this is tricky" are not; they warn without saying what of.
- **One idea per comment.** Two unrelated facts stacked in one block are two
  comments, each next to the code it is about.

### A comment does not pin volatile project state

A count, a version, a date, a list of the files that do something, the name of
whoever owns a thing — each is true when written and drifts the moment the project
moves, with nothing to notice. The comment is not merely stale afterwards; it is
wrong, and it is wrong in a way a reader has no reason to suspect.

Apply one test: **does the exact value change what the reader does?** Usually it
does not, and the sentence is better without it.

```text
# All 67 of these libraries are members of the ROOT bun workspace, so prettier,
# oxlint and tsc come from the root node_modules.
```

The load is carried by *all of them are workspace members*. The 67 adds nothing a
reader acts on and is wrong on the next library added. Drop the number and keep
the sentence. Same for `15 of the 67 declare a build script` — `some declare a
build script; the rest are source-shipped` says what the reader needs, and stays
true.

When the exact value genuinely is load-bearing — a pinned version another tool
must match, a threshold a measurement has to stay under — it is not volatile
state, it is a constraint. Keep it, and say what breaks when it changes. When a
reader would want the current number, point at the command that computes it rather
than writing the answer down.

### Duplication becomes a reference

The same explanation written in two places drifts: one site is updated and the
other goes stale silently, with nothing to detect it. When one fact is explained
in more than one place, pick a single canonical home and make every other site a
pointer to it.

- **Choosing the home.** For a fact about one function, its doc annotation. For a
  fact about a mechanism several call sites share, the declaration of that
  mechanism. For a project convention, the convention doc or standard that owns
  it — never a source file.
- **The reference form.** Code: a relative path and a symbol, as in
  `see writeJsonAtomic in lib/util/fs.ts`. Planning entities: a wikilink, as in
  `[[markdown-formatting]]`. Both are greppable, and both break loudly when
  the target moves.
- **Not everything repeated is duplication.** Two comments about the same subject
  that each carry a distinct local fact are two comments. Collapse only when one
  is genuinely a copy of the other's content.

Data is the sharpest case. A comment that lists the valid statuses, restates a
config default, or spells out a table's columns is a second copy of that data and
will disagree with the first one within a release. Point at the canonical
definition — the enum, the schema, the config file — and let the reader read the
values there.

#### A concept explained in code may belong in documentation

When a comment block explains a whole mechanism — the design of a subsystem, a
protocol between components, the reasoning behind an architecture — it has
outgrown the source file. Before keeping it, search the documentation for the
concept: the project's docs directories, its conventions, and any planning
or decision records (standards, decisions, principles).

- **The concept is already documented.** Replace the block with a wikilink to the
  entity or a relative path to the doc, keeping only the one line the reader of
  *this* file needs. Read the target first and confirm it says what you are about
  to stop saying here.
- **The concept is not documented and deserves to be.** Flag the gap, naming
  the concept, the file, and the entity kind that should own it. Leave the
  comment in place until the doc exists — the fact has nowhere else to live
  yet.
- **The concept is local to this one declaration.** It stays, tightened to the
  rules above. Not every explanation is a document.

## 5. Delta review

A delta review answers two questions: what changed since the last
review, and is the whole changeset still sound. Do both, in that
order.

First, get the last reviewed commit. `git fetch origin <last>` brings
it in when the branch was force-pushed and the commit is no longer on
it. If GitHub no longer serves that commit, fall back to a full review
and say so in the report.

Work out the shape of the delta:

- `git merge-base --is-ancestor <last> <head>` succeeds: the branch
  moved forward. The delta is `git diff <last>..<head>` and
  `git log <last>..<head>`.
- Otherwise the branch was rebased or amended. The delta is the
  interdiff: `git range-diff <last_base>..<last> <base>..<head>` at
  the commit level, and for the content
  `diff <(git diff <last_base>..<last>) <(git diff <base>..<head>)`.

Read the delta first, in full, and with the previous review beside it.
For each finding in the previous review, decide from the delta whether
it was addressed. Then read the whole changeset again with the delta
in mind. A change in one file can break an assumption in another that
the delta did not touch, and a fix for one finding can introduce a new
problem elsewhere.

Also read what the earlier rounds settled. From the `read` output of
step 3, take the findings with `status` `open` and the ones with
`status` `declined` together with their `reason`, and put both lists
into the prompt of the agent that judges the delta. The open ones feed
"Previous findings" below. A declined finding was answered by the
author and accepted or left alone: do not raise it again unless the
delta changed the code it points at so that it is true in a new way,
and then say what changed. `fixed` findings need no attention beyond
confirming the fix did not regress.

Report in three parts:

1. **New in the delta**: findings on lines the delta introduced, in
   the order of step 4.
2. **Previous findings**: one line each. Addressed, or still open with
   a short reason. Do not restate an open finding in full; link the
   earlier review comment, found by the `finding=<id>` marker among the PR's
   inline comments.
3. **Whole-changeset findings**: problems outside the delta that the
   previous review missed or that the delta made true. Say which.

The bar is the same as a full review (step 4). A finding is not new
because the delta is small, and it is not stale because it was raised
before.

## 6. Post

The order, per PR:

1. Re-check the markers (below).
2. `record` the findings.
3. Post the review.
4. `answer` each previous finding the delta review confirmed fixed (only those still `open`).
5. `release` the claim.

In `--mode ask`, show the draft first and ask whether to post it. In
`--mode auto`, post it.

Immediately before posting, fetch the PR's reviews again and repeat the
marker search from step 2. A marker for `head` that was not there at
step 2 means another session posted, which only happens when it took
over this claim as stale; release the claim and report
`REVIEW=claimed`.

Record the findings before posting, because the ids are in the posted
markers. Write the findings you are about to post, in order, as a JSON
array of `{ "path", "line", "title" }` (`path` and `line` are null for
a finding with no line in the diff). A review with no findings is allowed: post the summary only,
with the array empty, and still run `record` with `[]`: the round and the head belong in the
index.

```sh
node <skill-dir>/review-state.mjs record <number> --owner "<session>" --head <head> --base <base> --findings <file>
```

Its output lists `ids`, `{ index, id }` per finding. The state keeps no
comment URL (`comment` is optional and stays null); the marker in the
posted comment is what ties a comment to its finding, and a rebuild
reads it from there. `record` keeps the claim.

- Exit 4: another session took the claim over while this one worked.
  Do not post; report `REVIEW=claimed`.
- Any other failure: do not post. Release the claim, report the error
  and move on.
- If the post fails for good after a successful `record`, run the
  rebuild of step 3 so the unposted round does not stay in the index,
  then release the claim and report the error.

Post one review per PR per pass, and post it in two layers. Every
finding whose line is in the diff is an inline comment on that line,
so the author reads it next to the code. The review body is the
summary: the verdict, the test-coverage note, the findings that have no
line in the diff, and for a delta review the three parts of step 5. Missing coverage is a
finding, with an id and recorded, when it names a specific changed behaviour at a diff line that no
test exercises; otherwise it is one line in the summary with no id. A
review with findings and no inline comments is wrong; so is a set of
inline comments with no summary. Line comments go in the review itself,
anchored to the head commit:

```sh
gh api repos/<owner>/<repo>/pulls/<number>/reviews \
  --input review.json
```

with a body of this shape:

```json
{
  "commit_id": "<head>",
  "event": "COMMENT",
  "body": "<detailed review record>\n\n<summary>\n\n<!-- review-pr: head=<head> base=<base> actor=<actor> agent=<agent> at=<at> host=<host> session=<session> model=<model> effort=<effort> skill=<skill> mode=<mode> -->",
  "comments": [
    { "path": "<file>", "line": <line>, "side": "RIGHT", "body": "<finding>\n\n<short comment signature>\n<!-- review-pr: finding=<id> -->\n<!-- pr-tools: actor=<actor> agent=<agent> model=<model> effort=<effort> session=<session> skill=<skill> at=<at> -->" }
  ]
}
```

The body opens with the detailed review record from the shared instruction.
Its fixed row order makes two reviews readable side by side.

The event is always `COMMENT`. GitHub refuses an approval or a change
request from the PR's own author, and a review that states its verdict
in prose reads the same either way. The summary opens with that
verdict in one line (ready to merge, or what must change first).

`line` must be a line on the `RIGHT` side of the diff for `commit_id`, taken from the diff hunks and
not from a whole-file read. GitHub rejects the entire review with
`422 pull_request_review_thread.line must be part of the diff` when any one comment misses, and
nothing is posted. On a 422, retry once with the rejected comments moved into the summary as
`path:line` text; if the API does not say which comment failed, move them all. A finding in the
summary, whether it had no line or was moved, ends with its own `<!-- review-pr: finding=<id> -->`.
The summary-only review is what carries the marker, so a pass never ends with findings and no
marker.

The review marker is the last line of the body. Write both SHAs in full, and carry the shared
identity plus mode after them as `key=value` pairs, so a later pass or a dashboard can read the
record without parsing the table. `at=` is the pass start time from the shared identity, not the
posting time. After the post, record what the delta review confirmed. For each previous finding it
judged addressed and the index still lists as `open`, run
`node <skill-dir>/review-state.mjs answer <number> --id <id> --status fixed --fixed-in <head>` (the
full 40-character sha). A finding already `fixed` (check-pr answered it) needs no `answer`. Then
release the claim (step 3).

## 7. Report

Open with the shared identity, once for the whole pass:

```text
| Pass record | |
|---|---|
| Actor | @<actor> |
| Agent | <agent> |
| Model | <model> |
| Effort | <effort> |
| Skill | <skill> |
| Session | <session> |
| Host | <host> |
| Started | <at> |
| Mode | <mode> |
```

Then one line per PR, in this shape, so a loop can read it without
parsing prose:

```text
[#123](<url>) STATE=<open|draft|merged|closed> REVIEW=<full|delta|unchanged|skipped|claimed|closed> HEAD=<short sha> SINCE=<short sha|none> FINDINGS=<n> POSTED=<yes|no>
```

- `REVIEW=unchanged` means `head` matched the marker and `--mode auto`
  stopped there. `skipped` means the person declined a repeat review.
  `claimed` means another session holds the PR (step 3) or posted first
  (step 6); name the owner from the claim output when there is one.
  `closed` means the PR is merged or closed (step 1); nothing was reviewed.
- `SINCE` is the commit the last review covered, or `none` on a first
  review.
- `POSTED=no` with a non-zero `FINDINGS` means the person declined to
  post the draft; the draft is printed below the line.

Below the lines, add at most a few sentences on anything a person must
decide: a verdict of changes required, or a delta review that fell
back to a full review because the last commit could not be fetched.
When nothing needs a person, say so in one line.

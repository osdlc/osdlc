```sh
way --serve
```

This opens a page with the same catalog the terminal UI shows: a collapsible
tree by call chain, sticky group headers, fuzzy and exact search, and run and
copy buttons on every row.

It is a server, not a generated file. A file would be a snapshot. The server
probes, and the page refreshes on focus and every 15 seconds, so the page
shows what the repository has now. The server binds to `127.0.0.1`, and
every route needs a token. See [Security](#security).

`--port N` fixes the port. `--no-open` prints the URL instead of opening a
browser.

## Tabs

There is an `all` tab and one tab per runner, each with a task count. Tabs
follow the row groups: Tasks, then Dependencies, Tools and Git hooks, with a
labelled break where one group ends and the next begins.

Only runners detected in the repository get a report. A detected runner that
found no tasks folds into one "N empty runners" chip. **Runners** in the
toolbar opens the runner picker, which lists every runner with its count and
notes any that were withheld or failed.

### Reordering tabs

Drag a tab to reorder it. The order is saved in the browser's `localStorage`
and applies to the tab row, the runner picker and the top of the combined
tree. A saved order applies within a group. Groups always keep their own
order. A runner missing from the saved order goes at the end of its group.

## The tree

Tasks are grouped by call chain, with sticky headers.

- **Collapse** folds every group at once.
- **Scope** (Root, +2, +3, All) limits how deep to look, by where a task is
  declared. Root shows only what the repository root declares.
- **Declared** hides tasks no file declares. `cargo test` for a crate is
  synthesized from a convention, not written down.
- **Services** shows only tasks that run until you stop them. A dot in the
  leftmost column marks them.

## Run in terminal

Each row has a **run** button beside its copy button. It does not run the
task in the browser. It hands the terminal `way` is running in to the task.

After that the page is done. The server spawns the task and exits, so the
page has nothing left to talk to. The page replaces itself with "Handed off
to the terminal" and the command that ran.

What happens:

1. The page sends `POST /api/run` with the task's id and, for a task with
   parameters, a list of argument strings. It never sends argv, a command
   string or a directory. The server looks the id up in the catalog it built.
   An unknown id is a `404`.
2. The tool binds the arguments with its `invoke(task, args)`. The binary,
   the leading arguments and the working directory come only from the
   catalog. A tool whose `invoke` changes the binary is refused. Arguments
   that are not strings are dropped.
3. The server sends its response, stops, and spawns the task on its own
   stdin, stdout and stderr, without a shell.

There is one terminal, so only the first run wins. A second run gets a `409`,
and its row says "another run already took the terminal".

### Tasks that take arguments

For a recipe like `just deploy <env> [tag]`, **run** opens a bar at the foot
of the page:

```text
$ just deploy ▮
  takes <env> [tag]                    Enter run · Esc back
```

The command left of the field is fixed text. Only the arguments are yours to
type. Quotes group words as in a shell. There is no globbing, no variables and
no operators. `Esc` closes the bar with nothing run.

## Search

The page uses the same matcher as the terminal UI, so a query ranks the same
way in both. Terms are ANDed and fuzzy by default. A leading `'` makes a term
exact. The **Fuzzy / Exact** toggle switches the whole query.

## Keyboard

`/` focuses the search box.

While the search box has focus and a query is active, the top hit is marked
as the Enter target. Enter copies that row's command and moves focus to the
results list.

In the list, `↑` and `↓` move between rows and `Enter` copies the focused
row's command. `Escape` returns to the search box and keeps the query. A
second `Escape` in the search box clears it. Every copy button is also
reachable with `Tab`.

## Startup and the cache

The first `/api/catalog` request is answered from the
[stored probe](cache.md) when there is one, with a real probe running behind
it. The rows update in place when the probe lands. **Refresh** always runs a
real probe. Nothing is served from an empty store.

The status area reports stored rows the same way the terminal UI does:

- **Fresh**: nothing.
- **Stale**: `cached: just 35s old - re-probing`.
- **Stale and slow to probe here**, in the error colour.

The startup banner in the terminal reports the same thing. If you run a row
that no longer exists, the `404` names the cached listing and its age.

## Settings

The gear button opens this project's configuration as the server resolved
it: runners, execution, discovery and excluded paths. Each section names the
layer that supplied its value: this project, your user config, or the
built-in default.

### Editing

Runners, discovery and excluded paths can be edited. Execution cannot.

Edits are staged. A badge counts them and each changed section is marked
`unsaved`. Nothing is written until you press **Save to
wayfinder.config.json**. **Revert** drops the edits, and so does closing the
dialog. The file is usually committed, so a change to it should be a
deliberate act.

A save writes only the keys the screen owns and leaves other keys in the file
alone. The server refuses an unknown key, a value of the wrong type,
`allowExec: true`, and a request without the session token.

Where a dragged tab order is in force, the Runners section says so and offers
**Reset to configured order**.

### Trust from the page

Where a grant would change something, the page offers **Trust this
repository**: on a withheld runner, in the runner picker and in the Execution
section. It asks for confirmation. On a grant, the server returns a freshly
probed catalog.

**Untrust** is offered where the repository is trusted. It removes the stored
grant but does not change the running session. Start `way --serve` again to
probe without it.

Execution is shown, not offered as a toggle. A project file can only turn
execution off. Turning it on is the trust grant. See
[Trust and execution](trust.md).

## Themes

The theme button cycles System, Light and Dark. System follows the OS
setting. The choice is saved in `localStorage`.

## Security

The server binds to `127.0.0.1`. That is not a boundary on its own. Other
local users can reach the port and read a process's argv, and any site the
browser visits can send requests to it. So every route needs a token, and
there are two.

**The boot token** signs a browser in. It is 128 random bits in hex. It
appears only in the URL `way` opens (`/?boot=…`). The first request that
presents it uses it up. It expires 60 seconds after the URL is handed over if
no browser arrives. It works on page routes only, never on `/api/*`.

**The session token** is what the page uses after that. It is also 128
random bits, one per server process. It never appears in a URL or an argv. It
is embedded once in the served HTML, and the page keeps it in memory only,
not in `localStorage`, `sessionStorage` or a cookie. Every `/api/*` request
sends it in the `x-wayfinder-token` header.

A header is used instead of a cookie on purpose. A cookie rides along on a
cross-origin request from any site, which is CSRF. A custom header does not,
and it forces a CORS preflight the server never answers.

Two smaller points:

- Tokens are compared in constant time.
- Every page-route auth failure returns the same 401 page, whatever the
  cause. It tells you to stop `way` and start it again for a fresh link.
  Unknown paths also return 401.

`POST /api/trust` has one more check: the grant must apply to this run. It
returns `409` under `--no-exec`, under `--exec`, or when a config file turned
execution off. The token proves who is asking. It does not prove that the
request makes sense.

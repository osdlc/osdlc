```sh
way serve
```

This opens a page with the same catalog the terminal UI shows: a collapsible
tree by call chain, sticky group headers, fuzzy and exact search, and run and
copy buttons on every row.

It is a server, not a generated file. A file would be a snapshot. The server
probes, and the page refreshes on focus and every 15 seconds, so the page
shows what the repository has now. The server binds to `127.0.0.1`, and
every command needs a token. See [Security](#security).

Every action on the page is a command of `way`, called over HTTP. The list
and **Refresh** are `way list`, a trust grant is `way trust`, a saved setting
is `way config set`, and the tool info is `way providers`. The page and the command line read and write the same
files with the same rules.

`--port N` fixes the port. `--no-open` prints the URL instead of opening a
browser. Ctrl-C stops the server and any probe it is running.

## Tabs

There is an `all` tab and one tab per runner, each with a task count. Tabs
follow the row groups: Tasks, then Dependencies, Tools and Git hooks, then
Skills, with a labelled break where one group ends and the next begins.

A runner's **i** button opens what the tool is: its description, its
language and its homepage, then what each segment of its path means. The
homepage is a link only when it is `http` or `https`.

Only runners detected in the repository get a report. A detected runner that
found no tasks folds into one "N empty runners" chip. **Runners** in the
toolbar opens the runner picker, which lists every runner with its count and
notes any that were withheld or failed.

### Reordering tabs

Drag a tab to reorder it. The order is saved as `runners.order`, so `list`,
`query` and the terminal UI use it too. It goes to the project file when that
file sets `runners.order`, else to your user config, as the terminal UI's
settings screen saves it. It applies to the tab row, the runner picker and the
top of the combined tree. A saved order applies within a group. Groups always keep their own order. A runner
missing from the saved order goes at the end of its group.

## Skills

The **Skills** tab lists the agent skills the `skills` setting chooses: the
repository's own by default. Each row shows `/<name>` with its argument hint,
the agents that read it, its description, and where it came from. In the
`all` tab the skills are one group after the runners.

A skill is not a command. An agent runs it when you type `/<name>`, so
**copy**, `Enter` and `Shift+Enter` all put `/<name>` on the clipboard, and
nothing runs. The search matches skills as it matches tasks, and a query
ranks both in one list. **Services** and a runner's own tab show no skills.

## Narrow windows

At phone width the toolbar wraps, Scope, Services, Declared and Runners fold
into one **Filters** menu, and the tabs stay on one row that scrolls
sideways.

## The tree

Tasks are grouped by call chain, with sticky headers.

- **Collapse** folds every group at once.
- **Scope** (Root, +2, +3, All) limits how deep to look, by where a task is
  declared. Root shows only what the repository root declares.
- **Declared** hides tasks no file declares. `cargo test` for a crate is
  synthesized from a convention, not written down.
- **Services** shows only tasks that run until you stop them. A dot in the
  leftmost column marks them.

## Run in terminal

Each row has a **run** button beside its copy button. It does not run the
task in the browser. It hands the terminal `way` is running in to the task.

After that the page is done. The server spawns the task and exits, so the
page has nothing left to talk to. The page replaces itself with "Handed off
to the terminal" and the command that ran.

What happens:

1. The page sends `POST /run` with the task's id and a list of argument
   strings. It never sends argv, a command string or a directory.
2. The server resolves it as `way run <id> --dry-run -- <args>` does. The
   binary, the leading arguments and the working directory come only from
   the catalog. An unknown id is a `404`.
3. The server sends its response, stops, prints the command line, and runs
   the task on its own stdin, stdout and stderr, without a shell. `way serve`
   exits with the task's exit code.

There is one terminal, so only the first run wins. A second run gets a `409`,
and its row says "another run already took the terminal".

### Tasks that take arguments

For a recipe like `just deploy <env> [tag]`, **run** opens a bar at the foot
of the page:

```text
$ just deploy ▮
  takes <env> [tag]                    Enter run · Esc back
```

The command left of the field is fixed text. Only the arguments are yours to
type. Quotes group words as in a shell. There is no globbing, no variables and
no operators. `Esc` closes the bar with nothing run.

A `?` in the leftmost column marks a task whose parameters could not be
read, such as a recipe whose runner is withheld. Its **run** opens the same
bar, says why, and runs the task as it is when you press Enter with nothing
typed.

## Search

The page uses the same matcher as the terminal UI, so a query ranks the same
way in both. Terms are ANDed and fuzzy by default. A leading `'` makes a term
exact. The **Fuzzy / Exact** toggle switches the whole query.

## Keyboard

`/` focuses the search box.

While the search box has focus and a query is active, the top hit is marked
as the Enter target. Enter copies that row's command and moves focus to the
results list.

In the list, `↑` and `↓` move between rows and `Enter` copies the focused
row's command. Copy puts the argument vector on the clipboard quoted for the
server's shell, as the terminal UI copies it, not the Command column. A
command or skill name that holds a control character cannot be copied: its
copy button is disabled and says why. `Shift+Enter` runs the top hit or the focused row. `Escape`
returns to the search box and keeps the query. A second `Escape` in the
search box clears it. `?` opens the help, which lists the same keys. Every
copy button is also reachable with `Tab`.

## Startup and the cache

The server reads the view the last run saved (see [the cache](cache.md)) as
it starts, and starts a probe at once. It prints its address without waiting
for that probe. The page first asks for `way list --cached`, which the server
answers with the newest catalog it holds, then for `way list --join`, which
joins the probe already running or starts one; the polls do the same. The
rows update in place when the probe finishes, and until then the status says
`refreshing…`.

With nothing saved, the page's first read is the server's probe itself, and
each runner is drawn as it answers. A runner still out has a quiet tab and a
row with a spinner, and the status names them: `loading 3 of 12: just, mise,
moon`. A withheld or failed runner shows its reason as soon as it answers.
The lines come over the same API as every other call, as NDJSON (one JSON
line per runner, then the catalog document), with the same token and checks. **Refresh** always starts a probe. **Run** probes the
task's runner again first, and refuses a task that changed since the page
drew it.

The status area reports stored rows the same way the terminal UI does:

- **Fresh**: nothing.
- **Stale**: `cached: just 35s old - re-probing`.
- **Stale and slow to probe here**, in the error colour.

The startup banner in the terminal reports the same thing.

## Settings

The gear button opens the configuration as `way config list` reads it:
runners, execution, discovery, excluded paths and personal settings. Each
section names the layer that supplied its value: this project, your user
config, or the built-in default.

### Editing

Runners, discovery and excluded paths are written to the project file. Theme
and `open` are written to your user config.

Edits are staged. A badge counts them and each changed section is marked
`unsaved`. Nothing is written until you press **Save**, which names the files
it will write. Each edit is one `way config set`, and the notice after it
names each key and the file it went to. **Revert** drops the edits, and so
does closing the dialog. The project file is usually committed, so a change
to it should be a deliberate act.

`allowExec`, the `trust` policy and `tools` are shown read-only, each with
the command that changes it. The server refuses a write of them over HTTP.

Each runner row also says what its tool is, its language and, for an `http`
or `https` homepage, a link to it.

Where your user config holds a dragged runner order, the Runners section
offers to reset it.

### Trust from the page

Where a grant would change something, the page offers **Trust this
repository**: in the bar above the list, on a withheld runner, in the runner
picker and in the Execution section. It asks you first: the server answers
the first `way trust` with `428` and a one-time nonce, and grants only when
the page sends the request again with it. The next probe runs trusted.

**Untrust** is offered where a stored grant trusts the repository. It runs
`way trust --untrust`, and the next probe runs without it.

Trust can also be given to one tool. A runner that waits on one, such as a
mise task once another tool is trusted, says `withheld: mise is not trusted`.
The Execution section's **Tools** part lists those runners with a **Trust
mise** button, which is `way trust --scope mise` and asks you first in the
same way. It also lists the tools trusted on their own, each with
**Untrust** (`way trust --untrust --scope <tool>`).

Execution is shown, not offered as a toggle. A project file can only turn
execution off. Turning it on is the trust grant. See
[Trust and execution](trust.md).

## Themes

The theme button cycles System, Light and Dark. System follows the OS
setting. The choice is saved as `theme` in your user config, and the server
applies it before the page first paints.

## Security

The server binds to `127.0.0.1`. That is not a boundary on its own. Other
local users can reach the port and read a process's argv, and any site the
browser visits can send requests to it.

Every request passes two checks first. The `Host` header must name a
loopback address and this port, which stops DNS rebinding. An `Origin`
header, when present, must be this server's own. Either failing is a `403`.

**The boot token** signs a browser in. It is 128 random bits in hex. It
appears only in the URL `way` opens (`/?boot=…`). The page removes it from
the address bar and sends it once, in a JSON body to `POST /session`. The
first request that presents it uses it up, and it expires 60 seconds after
the URL is shown. The URL is in the browser opener's argv while the opener
runs, so another local user could redeem it first. If the right boot token
arrives a second time, it is refused with a `401` and `way` prints a warning
in its terminal. The server keeps running, and pages already signed in stay
signed in. Opening the old link in a second tab does this. If you did not,
stop `way serve` (Ctrl-C) and start it again. A new link does not help: a
program that signed in first keeps its session until the server stops.

**The bearer token** is what `POST /session` answers. It is also 128 random
bits, one per server process. It never appears in a URL, an argv or the
page's HTML. The page keeps it in `sessionStorage`, not in `localStorage`
or a cookie, and sends it as `Authorization: Bearer` on every command and on
`/run`. Without it, a request is a `401`.

`sessionStorage` belongs to one tab. It survives a reload, ends when the tab
closes, and is never sent with a request. So a reload stays signed in, but a
new tab or another browser is not. To sign one in, press Enter in the
terminal `way serve` runs in: it opens a new link, or prints it under
`--no-open`. Each new link retires the one before it. After a restart of
the server the old tab answers `401` and says the same. The terminal is
read only while `way serve` runs in the foreground, so `way serve &` keeps
serving; bring it back with `fg` to press Enter.

A header is used instead of a cookie on purpose. The browser sends a cookie
with a cross-origin request from any site, which allows CSRF. A header does
not, and it forces a CORS preflight the server never answers.

Commands that only the command line may run, such as a write of
`allowExec`, are refused with `403`. A trust grant needs the confirmation
described above. The page cannot lift `--no-exec`: every command the server
runs carries the flags `way serve` started with, and reads the directory it
started in. A directory named in the body is refused with `400`.

      The problem and the constraints

      We want to keep facts, such as how coding-agent harnesses behave, as a corpus: a folder of typed records that people browse and edit as plain files, and tools validate.

      Constraints:

      • Pure data. The corpus holds only records, schemas and one small root file. Every rule a tool enforces is written in the corpus or in the spec, never only in code. Schemas are JSON Schema 2020-12, not Zod or Rust types.
      • Browsable. File names read as what they are (Claude Code.md), in Finder, on GitHub and in Obsidian.
      • Many corpora in one vault. Several corpora can sit anywhere in one Obsidian vault, nested at any depth, beside ordinary notes. Moving a corpus must not break links into or out of it.
      • Links that work everywhere. A reference must resolve the same in our validator and in Obsidian.

      The prior art survey found mdbase (mdbase-dev/mdbase-spec) closest. We borrow its path and collision rules. We do not adopt its link resolution: mdbase resolves from each collection's root and treats every nested collection as a closed world, so links across corpora break there.

      What changed in revision 2. We tested the proposal in real tools. In Obsidian, moving a corpus that uses wikilinks rewrote the corpus's own files with vault paths ([[Archive/2026/harness-reference/harnesses/Claude Code]]), so the corpus stopped being portable. With relative Markdown links the corpus files did not change at all. Site generators confirmed it: Docusaurus, VitePress and MkDocs follow relative .md links natively, and none follows wikilinks without a plugin. So links inside a corpus are now relative Markdown links.

      Mini-apps and where to put corpora

      Use case: an app keeps its data as a corpus in a vault. A reading list, a task tracker, a set of inherited policies: an Obsidian plugin, CLI or small web app reads and writes records, and the user can still browse and edit them as notes. That adds four needs:

      1. Finding its corpus. Users move and rename folders, so an app needs a stable handle: an optional id in the root file (id: reading-list, or a UUID). The app scans for markdown-db.md and picks the one with its id. The folder name stays the corpus's name for links. 2. Writing records faithfully. A writer changes only the keys it owns and keeps key order, unknown keys and the body. Same rule as rust-ontogen's markdown-store and mdbase. 3. Concurrent edits. v0: whole-file writes, last writer wins. Apps that need merging follow mdbase's merge profile. 4. Upgrades. A schema version and migrations: deferred, but the root file leaves room for them.

      Placement guidance (non-normative). The spec lets a corpus sit anywhere; these are the recommended places:

      • In a vault: one top-level folder for structured data (Data/ or _data/), one corpus per app or dataset under it, named after it. Side by side, not nested.
      • In a code repository: corpora/<name>/, as harness-reference does.
      • Don't put a corpus inside another corpus's type folder.
      • Keep corpora that link to each other side by side in one folder.

      How should markdown-db relate to mdbase?

          1. A corpus is a folder holding `markdown-db.md` (or `.yaml` / `.json`)

          anchored to my-vault/ ├── .obsidian/ ├── markdown-db.md

          The marker's file name alone identifies a corpus. Its data (the spec version, later depends) sits in the frontmatter of markdown-db.md, or in the whole file for .yaml / .json. In the .md form the body is the corpus's front page, visible in Obsidian. Exactly one marker per folder. A corpus's name is its folder name.

              2. Nested corpora own their own subtree

              anchored to markdown-db.md corpus "harness-reference" (fron…

              my-vault does not own anything under Research/harness-reference/ or Research/skill-catalog/. Ownership decides which schema checks a record. It does not limit resolution: links resolve across the whole vault (see the resolution ladder).

                3. A type is a folder holding its own schema

                anchored to ├── harnesses.schema.md type "harnesses" (optional)

                The schema is named after its folder: harnesses/harnesses.schema.md (or .yaml / .json), so search and the quick switcher find it by the type name. A folder holding <its name>.schema.* is a type; any other folder is free-form narrative. An empty schema makes an untyped type.

                Records may sit at any depth below the type folder (google/Gemini CLI.md). Ids are file names and stay unique within the type.

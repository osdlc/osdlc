      The problem

      yaml-splice edits only top-level keys. To change build.target, a caller has to rewrite the whole build value, which loses the comments and quoting inside it. The plan is to add nested edits by path.

      The constraint: every guarantee the crate makes at the top level must hold at depth. Bytes outside the edit stay the same, an equal Set is a byte-identical no-op, every result is parsed and checked, and new values are written the way npm yaml writes them.

      The test corpus came first and now defines the behaviour. Writing it meant making decisions, and running the new character fuzzing against today's code found two bugs. This page asks you to settle both.

      Note: /craft:discuss has no domain note for code or YAML changes, so this page uses prose and annotated-text. A code domain note naming before/after YAML pairs as the solution block would fit pages like this one better.

      What exists now (uncommitted)

      In packages/rust/yaml-splice/tests/:

      • fixtures/nested.json: 143 cases across 14 categories and three tiers, plus 41 one-segment equivalence cases built from conformance.json. A self-check proves every expected output against an in-memory model of the edit.
      • neighbours_nested.rs: 7,500 documents and 180,000 planned edits, placing the existing value shapes one level down.
      • real_files.rs: 20 copied YAML files from this repo, with 1,870 planned edits.
      • fuzz_chars.rs: keys and values from 11 character groups, three tests, seeded and replayable. It runs against today's top-level edits.

      Everything passes. The nested tests report as pending until the code exists. The two fuzz findings are pinned as known counts. These files are not in the linked commit yet.

7. Fuzz finding: a key that starts with U+FEFF

Rename title -> "\u{feff}#c" on "title: Draft\nn: 1\n"
writes  "\u{feff}#c: Draft\nn: 1\n"
reads back as {n: 1}: the next reader drops the BOM and sees a comment

8. Fuzz finding: a value whose first non-empty line is only spaces

Set k = " \n"
the emitter writes  "k: |+\n   \n"
which reads back as "\n", so the crate refuses the edit
npm yaml 2.9.0 writes the same bytes and loses the space

9. Self-check finding: JSON objects arrive with sorted keys

Set b = {"k": 1, "j": 2}   (JSON in)
writes  b:\n  j: 2\n  k: 1    (keys sorted)
      Proposed API

      Three new FieldEdit variants: SetPath { path, value }, RemovePath { path } and RenamePath { path, to }. A path is a list of PathSegment::Key(String) or PathSegment::Index(usize). A one-segment path behaves exactly like today's Set, Remove and Rename.

      Three new EditError variants: PathNotFound, PathTypeMismatch and UnsupportedPath. Both enums are #[non_exhaustive], so adding variants is not a breaking change.

      Scope by tier

      Tier 1 is block mappings. Tier 2 is block sequences, including compact - key: items, where a key's column differs from its line's indent. Tier 3 is flow collections.

      In the real-file corpus, 642 planned edits need only tier 1 and 1,228 need tier 2. GitHub workflow steps are sequences.

      Fuzzing setup

      tests/fuzz_chars.rs uses a SplitMix64 generator with a fixed seed and no new dependency. It covers indicators, odd whitespace, line breaks (including NEL, LS and PS), control characters, multi-byte and combining text, bidi controls, case-folding traps (ß, İ, ı, ς, Kelvin sign), noncharacters, scalars that read as another type, and blank lines.

      It checks three things: each sample alone, random mixes, and corpus documents with characters spliced in. Four extra seeds at 50,000 iterations each found nothing beyond the two pinned classes. YAML_SPLICE_FUZZ_SEED and YAML_SPLICE_FUZZ_ITERS change a run.

                                  7. 7. Fuzz finding: a key that starts with U+FEFF

                                  anchored to 7. Fuzz finding: a key that starts with U+FEFF

                                  Any edit that leaves U+FEFF at byte zero (a renamed or new first key that starts with it, or a Remove that moves such a line up) makes the next reader drop it as a BOM. With # after it, the key and value are lost. The crate's result check misses it because it strips a BOM only from the input. npm yaml 2.9.0 writes the same unquoted key. Pinned in tests/fuzz_chars.rs as BOM_AT_BYTE_ZERO.

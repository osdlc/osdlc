      The problem and the constraint

      @osdlc/host-cleaner finds what git cannot see (build caches, Orca worktrees, stray Claude Code sessions) and cleans it with repo-cleaner's safety model. The current design, in PRs 943 to 948, gets there with two layers of hooks, and the owner's main goal, that several systems can watch the same data and that there will be many worktree hosts rather than only Orca, is where that design is hardest to extend. This page proposes a flat model in its place and checks it against the code.

      The constraint: nothing in the stack is merged, so the adapter contract in src/adapter.ts is not yet an interface that a scheduled job or a second adapter author depends on. Once it merges, changing it is a breaking change. The cheapest moment to change the shape is now, and the decision has to be made before the design review (host-cleaner-design) is applied to the record.

      Everything below is a proposal unless it cites a file; cited files are on branch sksizer/issue-666-scheduled-run (commit c8bb95ea), not on main. Where the code contradicts or complicates the model, the page says so in a block marked "the code says". How the model relates to the existing review's questions is in the last block before the questions.

      Why the current design is hard
      Sourcedocs/architecture/host-cleaner.md View GitHubpackages/ts/host-cleaner/src/registry.ts View GitHub

      Two layers. repo-cleaner takes a host with two hooks, annotate and removeWorktree (packages/ts/repo-cleaner/src/hooks.ts). host-cleaner takes adapters with six (detect, discover, gather, execute, annotate, removeWorktree) and merges the adapters' two repo-cleaner hooks into one of each before passing them down (src/registry.ts). An adapter has to know which layer each of its hooks lives in. The architecture page needs a table of "which adapter uses which hook" to explain it (docs/architecture/host-cleaner.md, "The hook model").

      Two kinds of row. repo-cleaner's rows (worktree, branch, remote) and the adapters' HostRows run through the same plan, check and receipt, but as two halves of each: HostPlan is { repo, rows } (src/plan.ts), HostReceipt is { repo, host }, and split() in src/clean.ts cuts every approval in two. Code that handles rows handles them twice.

      Order-dependent rules. chainAnnotate feeds each adapter's output to the next, so a later host "can override an earlier host's verdict" (the architecture page's own words). chainRemoveWorktree gives the worktree to the first adapter that returns non-null; if two hosts claim one worktree, the earlier one removes it and the other is never asked. The existing review asks whether that should be refused instead, and whether run order should be stated per host. Both questions exist only because the design has order.

      A takeover, not a notification. Orca's removeWorktree does not add to git's removal; it replaces it (src/orca.ts). The second host that also keeps a record has no way to be told. Anything a host must do after the removal, such as forgetting its record, has no hook.

      Repeated work. annotate runs inside the sweep and again inside every check and run. In src/orca.ts it calls listing(), which runs orca worktree list and orca terminal list, on every call, and removeWorktree calls listing() again per worktree.

      A change to the standalone tool for one host. The stack changes repo-cleaner in seven files (git diff --stat origin/main..origin/sksizer/issue-666-scheduled-run -- packages/ts/repo-cleaner: 142 insertions, 9 deletions), including the removeWorktree hook and the host:<name> blocker type.

      The plugin interface (proposal)
      Sourcepackages/ts/host-cleaner/src/adapter.ts View GitHub
      ts
      type Json = null | boolean | number | string | Json[] | { [k: string]: Json }

/** A small data packet one plugin proposes for deletion. The same shape for every kind. */
interface Candidate {
  id: string          // `<kind>:<path>`, unique in the list
  kind: string        // 'worktree' | 'branch' | 'remote' | 'artifact' | 'session' | ...
  path: string        // the thing itself; for a session, its working directory
  owner: string       // the plugin that deletes it, and the only one that may
  why: string
  bytes?: number
  evidence: Json      // the fingerprint: what the objections rest on. Re-check compares it
  requires?: string[] // candidate ids this one cannot go without (q-relations)
  unattended?: boolean // the owner says --auto may take it, if nothing objects
}

/** One plugin's objection to one candidate. Objections only add up. */
interface Objection {
  by: string
  candidate: string
  level: 'refuse' | 'protest'   // 'note' if q-levels says so
  code: string        // refuse: a blocker, e.g. 'live-process'. protest: the name --allow takes, e.g. 'discard-changes'
  reason: string
}

interface Plugin {
  name: string
  detect(ctx: Ctx): boolean
  scope?(ctx: Ctx): string[]                         // q-scope
  discover?(ctx: Ctx): Candidate[]
  object?(all: readonly Candidate[], ctx: Ctx): Objection[]
  prepare?(c: Candidate, ctx: Ctx): void             // before deleting c; every interested plugin
  delete?(c: Candidate, ctx: Ctx): string            // only for c.owner === name; returns the receipt sentence
  deleted?(c: Candidate, ctx: Ctx): void             // after; best effort
}

      Refinements of the owner's sketch: Objection.code (a protest needs a name --allow can grant), Candidate.requires and unattended (see the mapping and q-relations). object is given the list as read-only; a plugin cannot change a candidate or see another plugin's objections in the same pass. Existing types it replaces: HostAdapter, HostRow and HostStep in packages/ts/host-cleaner/src/adapter.ts.

      What the types mean
      Sourcepackages/ts/host-cleaner/src/clean.ts View GitHubpackages/ts/host-cleaner/src/plan.ts View GitHub

      Verdicts are derived, not stored. Today a row carries verdict, action, commands, risks and blockers (HostRow). In the proposal a candidate has none of them. A candidate with a refuse is blocked; one with only protests needs those names granted (today's review, or a delete with a risk); one with no objections is a delete. A repo-cleaner row judged keep is not proposed at all: it is not a candidate, and the git plugin can say why in its report. That loses the keep rows from host-cleaner's report (the standalone repo-cleaner CLI still lists them).

      Objections add up. The core merges every plugin's list. Any refuse blocks the candidate. Each protest becomes a risk the person must grant by name, with --allow <code> as today (split in src/clean.ts already treats an unknown name as a host risk). No plugin can lift another's objection, so the result is the same in any plugin order.

      One owner per candidate. Only the owner deletes a candidate. Any other plugin can object before and be told after. This is the whole "two hosts claim one worktree" problem: neither host claims it; the git plugin owns it, and both hosts are told.

      Re-check is the same rule. Run discover and object again and compare each picked candidate's evidence with repo-cleaner's sameFingerprint rule; a candidate now refused is dropped as blocked, one with a protest not granted as not-allowed, one gone as gone. These are the DropReasons selectHostRows already produces (src/clean.ts).

      The receipt has one step per candidate: who owned it, which plugins prepared, the delete result and verification sentence, and one line per notified plugin with its error if any.

      The code says: where the flat model needs more than the sketch
      Sourcepackages/ts/repo-cleaner/src/sweep.ts View GitHubpackages/ts/host-cleaner/src/artifacts.ts View GitHubpackages/ts/host-cleaner/src/auto.ts View GitHub

      Three places where the code is not as flat as the model.

      1. Candidates are related. The git plugin's candidates are not independent. repo-cleaner holds a branch when the worktree that would free it is held: holdFreedBranches runs after annotate in sweepRepo (packages/ts/repo-cleaner/src/sweep.ts, around line 530). Under additive objections the git plugin cannot see Orca's refusal of a worktree in the same pass, so it cannot hold the branch. Artifacts have the same shape: a target/ inside a worktree is deleted with the worktree, and failedIds in src/auto.ts already special-cases "a row gone because an earlier step removed its parent". Today repo rows run before host rows by construction. The model needs an explicit relation (Candidate.requires) or a path rule. That is q-relations.

      2. Discovery depends on discovery. cargo and node find target/ and node_modules by listing the worktrees of the roots the sweep read (checkoutsOf(ctx) in src/artifacts.ts; the context's targets are "the roots of the repositories the sweep read" when an adapter gathers). In a flat discover phase every plugin runs at once, so cargo cannot depend on git's output. Either plugins find roots themselves, from ctx.targets (as checkoutsOf already does by calling git worktree list), or there is a scope step that settles the roots first. That is q-scope.

      3. One step covers many candidates. repo-cleaner's archive pushes one archive branch per repository and verifies it before anything in that repository is deleted; a failed push stops the run, host rows included (clean.ts, archiveSteps, and q-archive-failure in the existing review). A per-candidate prepare does not fit that. The git plugin would run the archive lazily in the first prepare for a repository, and a failure there has to stop more than one candidate. That is part of q-prepare-fail.

      Prior art
      Sourcepackages/ts/observe/src/model.ts View GitHub

      Kubernetes admission webhooks. A validating admission webhook can only accept or reject; the API server calls every one and rejects the request if any rejects, so the order does not matter. Mutating webhooks rewrite the object and run in sequence, and the result depends on the order. host-cleaner's annotate chain is a mutating chain (each hook gets the previous hook's rows); object is a validating one. The proposal is the move from the first kind to the second. What it borrows: veto by any, no override. What it does not borrow: webhooks run before an object is persisted, ours run before deletion and again at re-check.

      Kubernetes finalizers. An object with finalizers is not removed until each finalizer's controller has done its cleanup and removed its name. prepare is the same idea. The difference matters for q-prepare-fail: in Kubernetes a stuck finalizer blocks the deletion indefinitely, which for a cleaner running unattended every six hours would mean a candidate that never goes and no one told.

      Kubernetes watch events. Watchers learn of a change after it has happened, independently, and cannot change it. deleted is that. Kubernetes keeps events in a stream a watcher can resume; the proposal asks whether we need that (q-deleted-mode).

      Git hooks are the version everyone knows: pre-* can refuse, post-* cannot.

      Inside this repo. I searched packages/ts and docs for a plugin or event pattern. There is no plugin framework. What exists: repo-cleaner's Annotate and RemoveWorktree hooks, which are the design being replaced; @osdlc/observe, which defines a session event model (packages/ts/observe/src/model.ts, lifecycle.ts, hook-payload.ts), which is a record of what happened rather than a set of hooks and so is a model for the deleted event log option, not for the pipeline; and a detect-harness catalog that the claude-code adapter already uses. Orca has its own orca plugin commands (scaffold, validate, inspect, in its CLI), but those extend Orca's UI and are unrelated.

      Plugin: git (this is repo-cleaner) (proposal)
      Sourcepackages/ts/repo-cleaner/src/clean.ts View GitHub
      ts
      const git: Plugin = {
  name: 'git',
  detect: (ctx) => ctx.targets.length > 0,
  discover(ctx) {
    // repo-cleaner's own sweep: worktrees, branches, remote branches, with evidence.
    const swept = sweep(ctx.targets, ctx.repoCleaner)
    this.rows = rowsByCandidateId(swept)           // kept for object(); re-made on each discover
    return swept.repos.flatMap(r => r.rows.filter(row => row.verdict !== 'keep').map(toCandidate))
    // toCandidate: id=row.id, kind=row.kind, path, owner:'git', evidence=row.evidence,
    //   requires = [worktree id] on a branch candidate that worktree frees,
    //   unattended = (row.verdict === 'delete' && row.risks.length === 0)
  },
  object(all) {
    // Its own rows' blockers and risks, unchanged: live-process, locked-worktree, ... -> refuse;
    // abandon-unmerged, discard-changes, confirm-open-pr -> protest. Nothing about others' candidates.
    return all.filter(c => c.owner === 'git').flatMap(c => objectionsOf(this.rows.get(c.id)))
  },
  delete(c, ctx) {
    // repo-cleaner's library step: refuses a live process and an unsafe force, runs the removal,
    // checks the directory is gone and git no longer lists it (and `archive` first, if asked).
    return removeCandidate(this.rows.get(c.id), { force: ctx.force, archive: ctx.archive })
  },
}

      The sweep already holds everything the objections need, so discover and object share one sweep per pass. this.rows is state kept between the two calls; the core calls them as a pair, and the re-check makes a fresh pair. removeCandidate is the library function that does what run does for one step today.

      Plugin: orca (proposal)
      Sourcepackages/ts/host-cleaner/src/orca.ts View GitHub
      ts
      const orca: Plugin = {
  name: 'orca',
  detect: () => cli() !== null,
  scope: () => orcaRepoPaths(),                // `orca repo list`, if q-scope adopts a scope phase
  object(all) {
    const listed = listing()                   // one `orca worktree list` and `orca terminal list` per phase
    return all.filter(c => c.kind === 'worktree').flatMap(c => {
      if (listed === null)                     // Orca cannot be asked
        return ORCA_WORKSPACES.test(c.path)
          ? [refuse(c, 'orca-unreachable', 'probably managed by Orca; start Orca and sweep again')]
          : []
      const w = listed.get(canon(c.path))
      return w ? [note(c, `Orca manages this worktree (${w.displayName}), ${w.terminals} terminals open`)] : []
    })
  },
  prepare(c) {                                 // just before git removes the worktree
    if (managed(c)) run(['terminal', 'close', '--worktree', `path:${c.path}`, '--all'])   // throws on failure
  },
  deleted(c) {                                 // after git removed it, best effort
    if (managed(c)) run(['worktree', 'rm', '--worktree', `path:${c.path}`])   // UNVERIFIED: see q-orca-forget
  },
}

      What it replaces: annotate and removeWorktree in src/orca.ts. The unreachable-Orca refusal, ORCA_WORKSPACES, canon and the CLI discovery are reused as they are. The note call is the new level in q-levels; without it that line is dropped.

      Can Orca forget a worktree that git already removed? (the key question)
      Sourcepackages/ts/host-cleaner/src/orca.ts View GitHub

      I read the Orca CLI's help, read-only, from /Applications/Orca.app/Contents/Resources/bin/orca: orca --help, orca worktree --help, orca worktree rm --help, orca worktree list --help, orca worktree set --help and orca terminal --help. I did not run any removal.

      What it says. orca worktree has list, show, activate, current, create, set, rm, ps. There is no forget, prune or deregister command. orca worktree rm --worktree <selector> is described as "Remove a Git worktree or a folder workspace entry from Orca", and "needs an explicit workspace ... as git worktree remove needs a path". Its note says that for a non-root folder workspace it "removes its Orca entry ... without deleting the folder or touching Git". For a Git worktree it describes a removal: it runs the repo's archive hooks only with --run-hooks, and it keeps or deletes the branch. Nothing in the help says what it does when the directory is already gone and git no longer lists it.

      So whether deleted can be orca worktree rm on an already-removed worktree is not documented, and I could not test it without removing something. It may succeed (Orca drops its record), fail with "not a git worktree" (leaving the record), or fail on the selector path: if Orca resolves a selector by looking at the disk. This has to be settled with a throwaway worktree before the plugin model can claim to need no takeover. Until then there are three ways forward, in q-orca-forget: verify and use rm as the forget step; have orca's prepare call orca worktree rm itself, so Orca removes the worktree and git's delete finds it gone (a takeover again, in different clothes); or let orca own the deletion of its own worktrees by kind.

      A related property the proposal gets for free: if Orca's record outlives its worktree for any reason (a failed deleted, or Orca being down when it ran), the next run's orca.discover can list a stale record as a candidate of its own kind, owned by orca. That needs orca worktree list to show such records, which I also could not verify.

      Cost: what survives and what is rewritten

      Survives as it is: the CLI shape, flags and exit codes (src/cli.ts, config.ts, bin.ts); the config file; the shared artifact layer (artifacts.ts: checkoutsOf, holdersIn, removeArtifact, sizeOf); the auto rules, the lock, the report and schedule with launchd (src/auto.ts, schedule.ts); repo-cleaner's whole engine and its safety model; the claude-code session reading and its SIGTERM sequence; orca's CLI discovery, schema parsing and canon.

      Rewritten: the contract and everything that handles it: adapter.ts, registry.ts, sweep.ts, plan.ts and clean.ts, which are PR 943 and the heart of the stack; the host half of HostPlan and HostReceipt; orca.ts from hooks to plugin phases; selectUnattended and cleanedIds/failedIds over the new receipt; the tests that assert on HostRow and on chainAnnotate.

      Size. The branch adds 6,269 lines in packages/ts/host-cleaner across 41 files (git diff --stat origin/main..origin/sksizer/issue-666-scheduled-run -- packages/ts/host-cleaner). I have not estimated the rewrite beyond the file list above, and it would be a guess to put a number on it. The core files are the part that changes; the CLI, the artifact layer, auto and schedule are the larger remainder.

      Risk of the model itself. It trades order for a few new rules: relations (q-relations), roots (q-scope), a place for batch steps like the archive (q-prepare-fail). Each is smaller than the chain rules it removes, but they are new surface, and the git plugin keeps state between discover and object that a pure interface would not.

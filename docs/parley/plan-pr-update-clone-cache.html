          Plan: pr-update clone cache and @osdlc/ecosystem

          One omnibus PR, built from ten reviewed slices, that delivers D-0005, D-ZVIA and osdlc/osdlc#1010.

          Goal, done and scope

          Goal. Build what D-0005 and D-ZVIA decided: pr-update runs a --repo target from a checkout already on the machine, or from a managed bare clone when there is none, and the osdlc tools share one repositories.yaml through a new package, @osdlc/ecosystem.

          How. All of it lands in one omnibus pull request to main, which you approve and merge. I build it as a series of slices. Each slice is its own pull request against the omnibus branch, so it gets full CI and its own reviews. I merge a slice into the omnibus only when it passes the review gate below. You review nothing until the omnibus is ready, except where a question here says otherwise.

          Done means:

          1. The omnibus is merged to main, and its Version Packages release has published @osdlc/config-layers, @osdlc/typed-git, @osdlc/trust-repo, @osdlc/cli-tool and @osdlc/pr-update (minor each) and the first @osdlc/ecosystem (0.1.0). 2. Every bullet of D-0005's Decision section has code and a test, listed in a conformance table in the omnibus body. 3. D-0005 says what was built, D-ZVIA says Accepted with the name kept, and osdlc/osdlc#844 is closed. 4. The published pr-update, installed from npm, runs survey on a repository with no checkout on this machine. 5. osdlc/osdlc#1010 is done: the trust store resolves through tiered-dirs, and pr-update's markers live under osdlc/pr-update/ (owner, 2026-11-23). 6. sdlc's change is open in its own repository, right after the release: it reads repositories.yaml and imports remote matching from typed-git (owner, 2026-11-23). You approve that one PR too.

          Out of scope (each gets a follow-up issue after the release, unless you say otherwise):

          • Moving devlink's files under osdlc/pr-update/. #1010 covers only the trust store.
          • A machine target for config set in cli-tool. pr-update mirror enable and disable cover it.
          • Project config at <repo>/.osdlc/pr-update.yaml.
          • B-0002 (a mirror-only value) and B-0003 (requiring git-ref attempts for clones).
          • Moving wayfinder or host-cleaner under the osdlc root.

          What I need from you, and when:

          1. Now: answer the blocking questions at the end and approve this plan, or send it back. 2. While I build: nothing, unless a finding would change one of your earlier answers. Then I ask once, on the omnibus pull request. 3. At the end: review and approve the omnibus. 4. After the release: approve sdlc's change in its own repository. 5. Right after the omnibus merges: stage @osdlc/ecosystem on npm and add its trusted publisher. Your npm account is needed, and the omnibus body has the exact commands. Until then the release workflow publishes nothing for any TypeScript package.

          How each slice is reviewed and merged
          Sourcestandards/review.md View

          Every slice passes all of these before I merge it into the omnibus. The tier comes from review.md. Every slice here is Deep, because each changes a public API, a stored file format, trust or credentials, or locking, so each gets two independent reviews, one from a different model.

          1. Author check. In the slice's worktree: pnpm install --frozen-lockfile, pnpm run build, pnpm run check, the package tests, and pnpm run check:packages. I read the whole diff as if someone else wrote it. Docs, README, the guide and the changeset are in the same slice. The PR description lists the D-0005 or D-ZVIA bullets the slice claims, each with the test that proves it. 2. CI green on the slice PR, the Windows tier-2 job included for any slice that touches paths, locks or git worktrees. 3. Review A, Claude, fresh context. A new session that has not seen the work runs craft's /code-review against the omnibus branch. It gets the diff and the decision records as the spec, not my summary. It checks correctness first, then spec conformance, design, tests, clarity and docs, and the Deep questions: what fails halfway, what an attacker controls, how it rolls back. 4. Review B, a different model. The local Codex CLI (0.167.2, read-only sandbox) runs the same rubric. The CI @codex workflow has only skipped in its last 100 runs, so I try it once on the first slice and use it only if it works. 5. Answer every finding on the PR: fix it, decline it with a reason, or verify it first. Each finding is checked against the code. A blocking or should finding is fixed, or declined with a reason both reviewers accept. Re-reviews cover what changed, and after the third round anything unresolved goes into the omnibus body under *For the owner*. 6. Merge. Squash, one commit per slice, a message in the repository's style, no attribution. Then I update the omnibus tracker (slice, PR link, rounds, findings, tests) and wait for the omnibus branch's CI to pass on the new head.

          Branch rules. The omnibus branch is never rebased or force-pushed. main comes in by merge, after each slice and before the final review. Slices are worked in their own worktrees and merged in the plan's order, so two slices never change the same file at once. The omnibus merges to main with a merge commit, as osdlc merges today, which keeps the slice commits for bisect.

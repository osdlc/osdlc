      What this review gates

      Two pieces of the plan in docs/planning/agent-ci.md (#713) are built and up as drafts:

      • #715 agent-call run: a command-line tool for @osdlc/agent-call. It reads a spec file, builds the prompt, runs one agent call and prints the result as JSON. Its tests pass, and one real claude call through it worked ($0.004).
      • #716 agent-setup: a composite action that installs a pinned claude, codex or cursor CLI and, optionally, plugins through skillwright. A real-runner test passed for all three harnesses; on claude, craft@osdlc shows as installed.

      The constraint: the next pieces (agent-pr-answer, and moving claude.yml onto a spec) build on these interfaces. Changing an interface after something depends on it costs more, so the decisions come first. Each question below has a recommendation.

      Dependencies as built

      Each arrow means "uses":

      • agent-setup (action) → the harness installers (claude's install script, npm for codex, cursor's build tarball) and the skillwright 0.7.0 binary for plugins. It does not use agent-call.
      • agent-pr-answer (action, not built) → the agent-call CLI, run with npx @osdlc/agent-call@<pinned> run.
      • agent-call → @osdlc/command-seam (as before) and now yaml, which only the CLI entry imports. The library's exports are unchanged.
      • skillwright → tradecraft-core → agent-adapt. These are Rust, in the skillwright repo.
      • harness-reference is not used by any code at runtime. agent-call and agent-adapt each keep their own copy of the facts, and only tradecraft-core's tests check against it.

      The direction holds. Facts sit at the bottom, then the file-level tools (skillwright over agent-adapt), then agent-call for one call, and the actions on top. Nothing points back down: agent-call doesn't use skillwright or agent-adapt, and the libraries don't use the actions.

      The gaps are below: one dependency, three spec fields, and four action interface details.

      agent-call run, as built (#715)

      agent-call run <spec.yml|json> [--agent id] [--root dir] [--input name=value|name=@file]... [--explain] [--dry-run]

      • Spec: it reads the spec's run: section: agent, model, strict, permissions (mode, allowTools, denyTools), prompt parts (file, text with {{input}}, input) and context (file, or input from name=@path). Unknown keys are errors.
      • Agent choice: --agent overrides run.agent, which overrides setup.harness.
      • Paths: file: paths stay inside --root; this is a lexical check that doesn't follow symlinks. The agent runs in the current directory.
      • Output: stdout is the normalized result as JSON. Exit codes: 0 ok, 1 agent error, 2 usage error, 3 strict refusal.
      • --explain / --dry-run: print the argv, env var names and every note, each tagged native, approximated, emulated or dropped.
      • strict: true: refuses the call on any approximated or dropped note.
      agent-setup, as built (#716)

      - Inputs: - harness: claude, codex or cursor. - version: empty means the default for the harness: claude 2.1.319, codex 0.162.0, cursor 2026.11.05-86047df. - marketplaces: one per line, as name=https-url [ref]. - plugins: one per line, as plugin@marketplace. - skillwright-version: default 0.7.0. - Output: cli-path. - cursor: its installer always installs the latest build, so the action downloads the pinned build's tarball from downloads.cursor.com, the URL cursor's installer uses. - Plugins: skillwright harness install <harness> --git-url <url> --vault <empty dir> --path <dir>/out --plugin <p> --yes. skillwright needs a vault even for a remote marketplace. For claude it rejects a ref. For cursor it only registers the marketplace. - Testing: DRY_RUN=1 prints the commands instead of running them. .github/workflows/agent-setup-test.yml runs the action for real.

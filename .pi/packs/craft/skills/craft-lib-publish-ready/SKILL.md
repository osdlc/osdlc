# `/skill:craft-lib-publish-ready`

Usage:

- `/skill:craft-lib-publish-ready <package dir> [options]` audits one package.
- `/skill:craft-lib-publish-ready <package dir> --re-audit <previous report> [options]` audits again
  and marks what changed since the previous report.

Options:

- `--ref <ref>`: the ref to audit. Default `HEAD`.
- `--release <version>`: the ref is the release commit for that version.
- `--out <report path>`: where to write the report. Default: return it as text. A caller that
  runs the skill as a subagent passes `--out`; the report is a deliverable, not a summary.
- `--home <owner/repo or path>`: the repo the library moves to. See
  [Drive a release](references/process.md#drive-a-release).
- `--first-version <max|replay|current|reset|X.Y.Z>`: the version strategy. Default `max`.
- `--changelog <replay|keep|summary|none>`: the CHANGELOG draft mode. Default `replay`.

Scope: the readiness audit of one package, the `audit` step of the
[process](references/process.md). Not in scope: fixing the gaps, deciding the gates (the
owner does that), and publishing.

Inputs: a package directory inside a git repository; the ref to audit, and whether it is the
release commit for a version; the registries it will publish to; the target home it will be
developed and released from; the owner's accounts and organisations on the code host; the
version strategy and changelog mode; and optionally a report path. Output: the report in the
shape below and the CHANGELOG draft, returned as text or written to the report path with
`CHANGELOG.draft.md` beside it. Both are always outside the package.

## Steps

1. Read the project's `CLAUDE.md` and `AGENTS.md` for rules that bear on packages. Read the
   manifest and pick the ecosystem file(s). Read the process, the bar and those files.
2. Pack the artifact as the bar's Audit target says. Copy the package at the ref to a scratch
   directory as the ecosystem file's Setup says, and run every build, pack, test and install
   command in the copy.
3. Read the package: manifest, README, CHANGELOG, licence files, every public item, the
   tests and any examples.
4. Run the process steps `name-survey`, `prior-art`, `stability` and `home`. Record each one's
   evidence and recommendation in the Gates table, and write the Version section from the
   replay, and from the twin's too when Q24 applies. When `--home` is set, `home` checks it
   against the evidence.
5. Write the API section as api-review says, and record the API gate in the Gates table.
6. Draft the CHANGELOG in the `--changelog` mode as changelog says. Record the mode, the
   left-out entries and the check result in the Version section.
7. Check every row of the bar with the ecosystem check for it. Record the command or file and
   line as evidence, and a verdict.
8. Write the owner questions: one per row with the owner verdict, one per gate, one for a
   `--home` the evidence disagrees with, the API questions api-review names, and the version
   questions version-replay names. Each has a
   recommendation and says what it settles.
9. Ask for each sign-off the process names, unless the decision notes already record it. Say
   where you looked.
10. Write the fix list: one item per gap or group of gaps, each naming its rows, a tag, the files to
    change and a done-when check. Tag each item as
    [Fix-list tags](references/process.md#fix-list-tags) says. When the chosen version or the draft
    differs from the package, add a fix item to apply them.
11. Check the report: every row has a verdict and evidence, every gap and blocker is in a fix
    item or an owner question, no fix item lacks a row, and every fix item has a tag.
12. Return the report and the draft, or write them to the report path and beside it.

## After the audit

The skill writes only to `--out` and the draft beside it, which are outside the package, or
returns both as text.

The caller may turn each fix item into a tracked task. The audit does not.

The report stays in the source repo and is never published with the package, because it
carries internal ids. The caller keeps it privately in the project's planning area, grouped by
audit kind and dated, for example
`docs/planning/audits/lib-publish-ready/<date>-<package>/report.md`. Fix tasks link to it, and
`--re-audit` reads it.

## Grading

- Every row of the bar appears in the report, with a verdict and evidence a reader can rerun.
- No step wrote inside the package directory.
- Every gate in the table has evidence and a recommendation.
- Every owner question has a recommendation.
- Every gap and blocker maps to a fix item or an owner question.
- Every fix item carries a tag, set by the
  [fix-list tags](references/process.md#fix-list-tags), and no `safe` item touches an API item
  flagged on the review page.
- The name survey and the registry checks carry dates.
- The Name and API gates show their sign-off as recorded or pending.
- The API section lists every public item with its example, and every flag is in an owner
  question or a fix item.
- The Version section's chosen version follows the strategy and version-replay's rules, is not
  below the floor, and the `Floor` line shows each name checked.
- Every uncertain replay row records how it was settled.
- When Q24 applies, the `Twin:` line shows both computed versions and the aligned result, and
  an owner question covers any explicit or release version that alignment would change.
- Every draft entry, except the `summary` description, traces to a replay row or a commit, and
  the report lists the entries left out.
- The mechanical check ran on the draft, and every hit is fixed or recorded as allowed with a
  reason.

## Test environment

A scratch copy of a small crate with these planted cases:

- a row it meets (pass);
- a dated CHANGELOG heading for a version with no tag, audited without `--release` (gap);
- a manifest entry that points a runtime at source it cannot load (blocker);
- no earlier published version (n/a for Q18 Versioning);
- an undecided platform list (owner);
- `license-file` with a custom licence instead of an SPDX `license` (owner, Q16);
- a release workflow that packs with a flag the audit would not use by default (the
  difference is recorded in `Artifact audited:`);
- no CI job on the oldest supported version (gap, Q11);
- a first-publish workflow that uses a long-lived token with no protected environment (gap, Q22);
- an exported helper that looks internal (flagged `internal`, an API owner question, API gate
  pending);
- a stable public item with no example (flagged `no-example`, a Q8 fix item);
- a history merged with merge commits, where one PR has several commits (one replay row);
- a feature branch merged into an integration branch, then the integration branch merged into
  the default branch (one replay row, one bump);
- a package moved from another directory, with a breaking change before the move (the replay
  starts before the move and counts it);
- a breaking change after the first commit, which the replay counts as a minor bump;
- a manifest version above the replayed version, which `max` keeps;
- a TypeScript twin package beside the crate (same name under `packages/ts/`), whose behaviour
  change landed in one twin only and whose CHANGELOG names no twin version (Q24 gap; the draft
  for the crate names the twin version);
- a twin whose major.minor differs from the crate's (Q24 gap; an aligned version in the Version
  section's `Twin:` line; an `Aligned with` line in the draft; with `--release` set to a
  different version, a Q24 owner question instead);
- a commit message that names a person and links a private PR, which must not reach the draft.

A second fixture covers the floor: a crate whose rename history gives an old name that is an
existing crates.io crate with a known highest version above the replay, recorded in the test
(the floor wins, and the Version section's `Floor` line names that crate). It has no case
for "no earlier published version".

Run the skill on it. Expect each case in the rows, the gap and blocker in the fix list, the
owner cases in the questions, and the package directory unchanged (`git status` clean, no new
lockfile). Expect the draft beside the report, with no name or private link in it. Then run:

- with `--release <a version other than the chosen one>`: the chosen version is the release
  version, Q19 passes, and an owner question names the strategy's version;
- with `--first-version replay`: the replayed version, unless the floor is higher;
- on the floor fixture, with `--first-version 0.1.0` or `--release <below the floor>`: the chosen
  version stays as given, with an owner question under Q18 naming the floor and no fix item;
- with `--first-version reset`: `0.1.0` (the floor on the floor fixture), and a draft
  with no history section;
- with `--changelog keep`, `summary` and `none`: the sanitized old file, one descriptive entry,
  and an empty Unreleased section;
- with `--re-audit` after a commit that sets the chosen version and adds a fix: the same chosen
  version, and the fix in its Unreleased entry.

---
'@osdlc/cli-tool': minor
---

A CLI can now be declared as a tree of commands. The new `@osdlc/cli-tool/command` entry has `defineCommand`, `defineGroup`, `commandKit` (for typed global flags) and `defineApp`. Each command declares its flags, arguments and a Zod output once. The app routes the command line, prints the output as text, or under `--json` as one document that starts with `schemaVersion` and `kind`, and adds `help` (with `--depth`, `--full`, `--all` and a JSON form), `schema` (each command's input and output JSON Schema), `--help` on every command and `--version`. `loadCommandTree` builds the tree from a directory of command files. Zod is a peer dependency of these entries; the root entry still does not load it.

Shared commands: `@osdlc/cli-tool/config-command` (`configCommands(store)`), `@osdlc/cli-tool/trust-command` (`trustCommand(service)`) and `@osdlc/cli-tool/guide` (`guideCommand(topics, { title })`). Each takes the tool's own store, trust service or topics. `@osdlc/cli-tool/testing` has `runApp`, `checkApp` and `checkGuide` for a tool's tests. All of these are experimental.

Every command's context has `ctx.globals`, the app's global flags (such as `-C <dir>`), parsed once before the command runs. Under `--json` or `--output jsonl`, a failure prints one error document on stdout, `{ schemaVersion, kind: 'error', code, message, exit, hint? }`, as well as the message on stderr. `ErrorDocument`, `ErrorDocumentSchema` and `errorDocument()` describe it, and `CommandError` takes a `code` (a `UsageError` is `'usage'`). The `kind` and `schemaVersion` of a document always come from the command, whatever the output object holds.

Checks when the app is declared: a flag may not reuse a built-in name (`help`, `json`, `output`, `version`) or the short `-h`, two flags may not share a short letter across the globals and a command, exit codes 22-25 are reserved, and an `items` element may not declare `schemaVersion` or `kind`. `loadCommandTree` takes an absolute directory only, skips symbolic links, and refuses a file or directory name that is not a plain word (letters, digits, `-` and `_`).

Shared-command details:
- `trust --scope` is checked: `TrustService.parseScope` (pass `@osdlc/trust-repo`'s `parseTrustScope`) or a default check, and `*` is refused; either refusal exits 2. A service with `untrustAll` adds `trust --untrust-all`. `trust --untrust` on a root that policy still trusts says so.
- `ConfigStore.resolveKey` maps a typed key to its canonical name, so `cliOnlyKeys` cannot be dodged by case or `a[b]` spelling. Without it, keys are compared lowercased with `[x]` read as `.x`. `parseConfigValue` refuses a number that is not finite, such as `1e400`.
- Text from a repository or a config file is printed with control characters removed.
- `runApp` runs in a scratch working directory and a scratch home by default, so a test never reads the real `~/.config`. Pass `cwd` and `env` to choose your own. It also checks an error document against `ErrorDocumentSchema`.

The root entry adds `wrapText`, `helpWidth`, `columns`, `colorEnabled` and an optional `CliContext.terminal`, which `processContext()` fills in; the new `@osdlc/cli-tool/wrap` entry has the text helpers alone. `wrapText` keeps list items, `$ ` command lines, tables, fenced code and lines ending in `:` as they are. `colorEnabled` uses `@osdlc/ux`'s `detectColorLevel`, now a dependency: a non-empty `NO_COLOR` turns color off first, then `FORCE_COLOR` decides by its exact value, then `TERM=dumb`, then whether stdout is a terminal. Two cases differ from a plain `NO_COLOR`/`FORCE_COLOR` check: `FORCE_COLOR=0` or `false` turns color off even on a terminal, and a `FORCE_COLOR` value that is not a known level is ignored. `defineCli` takes an optional `width`; with it, epilogues are reflowed and help wraps at that width. Without it, help renders as before.

Breaking, for devlink users on macOS: link state moves from `~/Library/Application Support/<tool>/` to `${XDG_CONFIG_HOME:-~/.config}/<tool>/`, the `xdg` convention, and the launcher reads it there. Run `<tool> dev link` again to restore a link, or move the `home` and `history.jsonl` files. Linux paths do not change. The convention is fixed: devlink sets `conventionFromEnv: false`, so a `<TOOL>_CONVENTION` variable does not move the state away from where the launcher reads it. When a link is still in the old macOS place, `dev status` says so and prints the `mv` command that moves it. `runDevCli` on Windows now prints that `<tool> dev` is not available there and exits 1. A committed launcher must be rendered again (`launcherDrift` reports it).
